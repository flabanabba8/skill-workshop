# Verification

## Skill Workshop 0.3.3 (the suite)

- **0.3.3:** Maintainer review. Probe subprocesses get a minimal environment; the email pattern is length-bounded and each result is scanned once across the two hooks; skill folders come from hermes_cli.config.load_config(); miner wording states plainly that it reads local session history; requires_hermes >=0.23.0. Re-tested: 113 offline tests, all passing. Live test through Hermes 0.23.0 (2026-11-12, own profile): miner scan, Skill Guard scan and the builder resources report ran; no key values appear in any result.
- **0.3.2:** Shield handles Markdown image labels, JSON string values and shell continuations, and exact trusted URLs are honored without trusting other URLs on the same host. The trust approval names its destination. Skill Guard applies the approved directory decision to a matching linked-file view, including after restart. Live tests and limits are in the local live-test report.
- **0.3.1:** Shield extracts commands from markup, prose and inline code, normalizes zero-width characters, and exempts commands the user typed. Decision approvals identify the requested skill and decision; batched skill writes identify their target and track successful writes. Live tests and remaining limitations are recorded in the local live-test report. The real-skill scan remained 3 flagged out of 116, unchanged from 0.3.0.

- **New in 0.3.0, Skill Guard (scan skills from other people) and a Miner fix:** `guard/` scans every skill that reaches Hermes. Tested offline with fake skills folders (23 tests, no Hermes running; external skill folders are read from config.yaml directly): a `skill_manage` create, edit, patch, write_file or batched write with findings asks with each finding (file and line) in the approval text, and a clean one passes silently; a `write_file` into the skills folder is scanned and one elsewhere is not; a poisoned skill dropped straight into the skills folder is replaced by a warning at `skill_view` (named findings, told once, flagged text not repeated); a `/skill-name` message is blocked before the model; a clean third-party skill passes silently and is scanned once (counted); a changed file, including a bundled script, is scanned again; an approved version is not asked again but a changed one is; quarantine survives a restart (`decisions.json`, mode 0600); a skill reported by `on_skill_lifecycle` (as a hub install is) is scanned and mentioned once at the next turn; `skillguard_scan_installed` lists each skill with file and line; `skillguard_decide` needs a person; a crash inside the guard does not break a hook. The false-positive tightening of the scan is tested with 8 ordinary lines (all clean) and 8 attack lines (all still flagged). On the author's own folders (116 skills) 3 are now flagged, down from 9: all three pipe a vendor's install script into a shell, which is the rule working as intended; the six removed were prose or placeholders (advice "don't tell the user to ...", a quoted `[system]` placeholder, a quoted `<instruction>` argument, a defensive skill quoting an attack phrase, a table row describing a blocked pattern, a note about an environment variable). The Miner now leaves out housekeeping calls and ranks by request wording, file types and write steps (5 tests: four chats of one chore each opening with skills_list, search_files and skill_view yield read_file then write_file named from the request, held-out check and replay still pass).
- **Hermes source read for this (v0.23.0, read-only):** the agent tools that change skills are `skill_manage` and the ordinary `write_file` and `patch`; the tools that load one are `skill_view` (and `skills_list`, names only); hub installs (`hermes skills install`) run from the command line and register no agent tool. **Hooks Hermes does not expose:** nothing fires before a hub install or a manual copy (only `on_skill_lifecycle` "installed" after it landed), so those are scanned after the fact and held back at use time; a `/skill-name` command and a preloaded skill call `skill_view` in Python, not through the tool path, so the `transform_tool_result` hook never sees them and the Guard checks the user message in `pre_llm_call` instead (assumed to carry the skill text; not confirmed live); a file written with a shell command is not seen until it is first used.
- **Limits:** not every case has been run in a live Hermes session with a model (the approval box text, the warning replacing the skill, the slash-command block, `on_skill_lifecycle` after a real hub install and the next-turn notice are exercised only with fake inputs shaped like Hermes's calls). The rules were tuned on the author's own 116 skills, so the false-positive rate on other people's skills and the detection rate on rephrased or encoded injections are unknown.

## Skill Workshop 0.2.0 (the suite, earlier record)

- **New in 0.2.0, scan before install:** `skillscan.py` applies the Shield's own patterns line by line to a skill before `miner_install` or `skillbuilder_install` writes it, and `shield_scan` takes a `path` for a downloaded skill file or folder. Tested offline (see the test count below): a clean draft installs with `scanned for prompt injection: no findings`; a draft with a hidden HTML-comment instruction, one with zero-width text and one with an exfiltration command are each refused with findings and line numbers and nothing is written; the override path returns an approval whose text lists the findings and still installs only through `allow_findings`; the two skills the live test installed (`meeting-notes-one-pager`, `project-context-discovery`) and the plugin's own three skills scan clean; and 80 of 85 skills found in the author's own Hermes skills folder scan clean (the 5 flagged are installer-script lines that pipe a download into a shell, or a stray phrase, which is the intended behaviour). Not tested: a live Hermes session through the on-screen approval box with the new block/override text (the hook returns the same `approve`/`block` shape the Shield already uses live); an independent corpus of malicious skills, so the detection rate on rephrased or encoded injections is unknown; bundled files other than `SKILL.md` are scanned only by `shield_scan` with `path` because the two install tools install `SKILL.md` alone.

- **Tests:** the three parts' own offline tests, adapted to load the whole suite as one plugin, plus a suite test. From the plugin folder they run with `python -m unittest discover -s tests -t .`: 105 tests pass at 0.3.2 (102 at 0.3.1; 98 at 0.3.0) (26 Skill Miner, 16 Skill Builder, 17 Taint Shield, 8 suite, 10 scan-before-install, 24 Skill Guard; 70 at 0.2.0), also with ResourceWarning as an error (unittest is the supported runner; pytest collection is not set up). The suite test checks that `register()` exposes exactly the 16 tools and the hooks declared in `plugin.yaml`, once each, with nothing else registered; that each part's skill file exists; that the tool reference in `llmwiki/tools.md` lists exactly the registered tools; that every link in the wiki and the skills resolves; that the two install tools still ask for approval; and that each part gets its own folder under one suite data folder.
- **Hermes admission:** `hermes plugins validate <clean export of the commit> --install-deps` with Hermes v0.23.0 in a disposable Hermes home: all checks passed (manifest, `requires_hermes`, loadable, no Python dependencies, the capability probe matched the declared tools and hooks, no built-in tool collisions, security scan safe, no core override) with no warnings. The only extra line is the informational `Isolation - runs in the plugin host`.
- **Workflow preflight and secret/identity audit:** both clean on the tree and the history before release.
- **What the suite changes from the stand-alone plugins:** the parts are copied in as sub-packages with their behaviour unchanged. Three things differ: data folders are now sub-folders of `plugin-data/skill-workshop/` (data from the stand-alone plugins is not migrated); the skill and wiki files moved under the suite's `skills/` and `llmwiki/`; Taint Shield's hook is registered before the two install-approval hooks. The parts' provenance hash lists were dropped because they described the old file layout.

## Live evidence belongs to the parts

The live runs and the demonstrations of each part were made with the stand-alone plugins, not with this bundle. They are described in each part's own record, kept below in short form. Nothing here claims a live run of the bundled plugin.

### Skill Miner (stand-alone 0.2.1)
- 21 offline tests on synthetic session databases: repeated-workflow detection, held-out replay, redaction, diagnose size and redaction, refine keeps the original bytes, check per item, gated install, retired-workflow refusal, human skill names.
- A read-only scan of the author's real 90-day history (72 sessions with tool calls) found 6 candidate patterns and recommended none.

### First Principles Skill Builder (stand-alone 0.1.0)
- 16 offline tests cover every helper, the lint on a deliberately bad and an improved draft, revisions, cases, install gating, bounded resource output and registration.
- A real Hermes session built a skill for turning meeting recordings into searchable notes: revision 1 failed the degraded-mode check, revision 2 passed; three contrasting cases were recorded; nothing was installed. Defects found there were fixed in source.

### Taint Shield (stand-alone 0.2.2)
- 15 offline tests, including a small hand-written corpus of 9 injected pages with the actions they try to cause (all must be stopped) and 7 ordinary agent flows (all must be left alone). The corpus is written by the plugin author and is not an independent benchmark.
- Through Hermes's real tool path in a throwaway home: an injected page was recorded by the real `post_tool_call` hook, the real terminal call for an exfiltration command was blocked and never ran, and a normal `echo` ran.
- Live demo runs found and fixed: a copy of a secret-named file after an injected phrase was not stopped; the file reader's JSON output hid command lines from the detector.
- Not verified: a live agent session with a real model reading a real hostile page beyond those demo runs, rephrased or encoded injections, the false-positive rate on long real sessions, Windows.

## 0.3.4 - sessions are read through hermes_state (2026-11-12)

The miner no longer opens `state.db` with its own SQL. It reads sessions and messages through Hermes's public `hermes_state.SessionDB` (read-only: `list_sessions_rich`, `get_session`, `get_messages`), as the maintainers recommended in review, so a core schema change does not break it. The miner tests now build their session stores through `SessionDB` too instead of hand-made tables.

- Tested here: 114 Python tests, also with ResourceWarning as an error, run with the Hermes Python and `HERMES_DISABLE_LAZY_INSTALLS=1` against one test `HERMES_HOME` (importing `hermes_state` under a fresh home triggers Hermes's own dependency installs).

## 0.4.0 - miner_session, one session into a skill (2026-11-13)

New tool `miner_session` (17 tools now). What the Miner already had: `core.load(ids=...)` could read one session, but it kept only the first user request, nothing after it, and drafting needed a multi-session pattern from `miner_scan`. Added: ordered steps with argument shapes, retries and polling collapsed, failures with what replaced them; the user's later messages split into preferences and one-off facts by a word-pattern heuristic (each quote carries its message number and reasons); a saved draft with a "Preferences from <date>" section that then uses the existing diagnose, refine, check, scan and confirmed-install path (verdict `single_session`, replay check skipped because there are no held-out sessions).

- Tested offline: 26 new tests (tests/miner/test_session.py): retries, failed steps and polling; preference versus one-off; redaction of paths, URLs, emails, keys and file names; an injected instruction in a tool result and in a failed command (returned quoted and flagged, kept out of the draft, and a draft that copies it is flagged by the scan); empty, housekeeping-only and tiny sessions; tools of plugins that are not installed; a retired workflow is refused; picking by id, title, date and current session. 140 tests pass in all.
- Real run (a copy of the author's own session store; the original was not touched): one 138-message session: 40 tool calls became 15 steps (9 housekeeping calls dropped, 2 polling runs merged), 3 failures each with its replacement; 3 preferences found, 1 clearly right, 2 are corrections of one-off facts; 5 one-off facts; 29 messages unclassified, mostly one-off task requests. One 659-message session: 301 tool calls became 147 steps (31 housekeeping calls dropped, 22 polling or retry runs merged); 7 preferences found, about 3 right (a rule to always use a named tool, to plan before implementing, a "do not change my rules" correction), the rest false positives (a Hermes hand-off request and a few complaints); it missed several corrections phrased as questions ("why do you keep ..."). Output contained no home path, user name, URL, email or key. A third session was refused because it used a retired workflow, as miner_propose would.
- Not verified: a live Hermes session with a model writing a skill from the result; whether the host passes `session_id` to the handler (when it does not, the most recent session with tool calls is used); sessions that were split by context compression are read as separate sessions.
